How an AI order works

Chat / Voice Order Flow

The LLM converses; deterministic code decides. Nothing is saved until the guardrail passes and the customer confirms.

1Message inText, or voice transcribed by Deepgram over the live call
2Input guardrailBlocks prompt injection & abuse; detects EN/HI per turn
3Agent + LLMLive menu in prompt; stage decides which tools it may call
4Price via corecompute_bill() — engine computes, LLM only reads the result
5Bill injectionBill UI pushed straight to the frontend, bypassing LLM generation
6Confirm + validateOutput guardrail re-validates name, phone, items, qty before any write

Engineering Discipline

Best Practices We Applied

The practices that made a ~40,000-line, 6-surface system stay stable while being built by multiple contributors (human and AI) across 118 commits and 33 merged pull requests.

01 Pure, frozen core (single source of truth)

core/ has zero web, DB, or LLM imports. Every surface — Gradio, REST, POS, the AI agent — calls the same pricing and validation functions in-process. One brain, many faces: money can never be computed two different ways.

02 Additive layering & graceful degradation

Every new layer is additive: the graded app runs with nothing but menu files; DB writes are best-effort with retry; observability failures never reach a customer. Removing any upper layer leaves a working system.

03 The LLM never computes money

The agent orchestrates but all arithmetic goes through compute_bill(). Tools are stage-gated — the model can't even see "save order" until a bill has been priced and is awaiting confirmation. Deterministic outputs (bills, confirmations) are injected into the UI, bypassing token generation.

04 Guardrails on both sides of the model

Input: heuristics + a cheap LLM classifier block injection and abuse (fail-open so a classifier outage never blocks ordering). Output: before any write, the order is re-validated by the same core/validation rules the graded app uses.

05 Defensive input handling everywhere

Menu files can be swapped or corrupted; users type "three" as a quantity. Every validator returns (ok, value | message) and callers re-prompt — nothing raises, nothing crashes. All eight graded edge cases are pinned by tests.

06 Tests that run anywhere

199 tests run with no API keys and no database — lazy config plus monkeypatched in-memory fakes. A pricing regression test pins the exact graded bill (₹3,594.87) so the engine can never drift silently.

07 Security by default

bcrypt-only credential hashes, HS256 JWTs with per-endpoint require_role() guards, 5-failure login lockout for 6-digit PINs, bandit static scans on every commit, and secrets kept in .env — never in git.

08 Isolation as an architecture rule

Frontend surfaces live in separate route groups that never import from each other; shared modules (components/ui, lib/api.ts) are additive-only. One surface can be rebuilt — even by a different developer or an LLM — without risk to the rest.

09 Design tokens, not hex codes

All colors are semantic CSS variables per [data-theme]; components read tokens like bg-primary. Swapping the entire brand palette is a one-attribute change — proven live when the default theme changed with a 3-line diff.

10 Full observability & resilience for AI

Every LLM call is traced in Langfuse (model, tokens, cost, tool calls) and surfaced in an in-house ops dashboard. A three-model fallback chain (Gemini → Claude → GPT) plus a capped tool loop means a provider outage degrades to an apology, never a crash.

11 Versioned schema migrations

22 numbered SQL migrations evolve the database from first schema to inventory, coupons, and sentiment — reviewable, ordered, and reproducible in any environment.

12 CI-gated, convention-driven delivery

Feature-branch workflow with 30+ reviewed PRs; GitHub Actions runs the full test suite on every PR (failing tests block merge) and auto-deploys master to Hugging Face Spaces. Pre-commit formatting, linting, and security scans keep every commit clean.

Conclusion — Why It Matters

What Mr. Rajan Sharma Gets

SliceMatic's founder runs one outlet in New Ashok Nagar doing ~47 orders/day at a ₹847 average order value (~₹9.96L/month net revenue, ₹644 contribution per order — Stage 1 unit economics). Here is what this platform changes for him, in his numbers.

₹ His own channel — zero commission

Aggregators take 25–30% of every delivery order. His projected delivery revenue is ~₹6.6L/month — routed through Swiggy/Zomato that's ₹1.7–2L/month in commission. Orders through his own chat, voice, and app channels keep all of it.

₹ An order-taker that costs ~₹2 per order

Today one counter + billing staffer (₹18,000/month — his 3rd biggest salary) answers the phone and keys in orders: ~₹13 of labour per order, one call at a time, during shop hours only. The AI takes orders by chat and live voice, in Hindi and English, 24/7, at ₹1–2 per conversation — and frees that person to serve walk-ins.

₹ Every bill exact, zero leakage

One frozen engine computes every price — 10% bulk discount, 18% GST, 2-decimal rounding — across chat, voice, app, and counter. No mis-keyed bills, no "special price" at the counter, no GST arithmetic mistakes at tax time.

📊 No more operating blind

His Stage 1 pain point was "no data — operating blind on unit economics." Now every order is a structured record: sales analytics, item mix, feedback sentiment, and AI insights in the admin console — the data to steer the menu toward high-margin items.

🛡️ Tighter operations, less shrinkage

Role-gated accounts for staff, kitchen, and riders; timestamped status at every hand-off; recipe-based inventory deductions and audit logs. He can see exactly where every order and every ingredient went — from home.

🗣️ The whole neighbourhood can order

Voice calls and Hindi support mean customers who would never install an app or type in English can still order directly. Escalation to a human is one sentence away, so nobody gets stuck talking to a machine.
